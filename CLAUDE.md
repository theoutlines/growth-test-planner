# growth-test-planner — project memory

The live Growth Test Planner: https://planner.theoutlines.xyz. Author: Ivan Polushin (theoutlines). Public repo; code MIT.
Design source of truth: the Claude Design canvas https://claude.ai/artifact/FDAgypvxoZ6MnD4w8D3urr (page "System (v4)"), and the design notes in the owner's paywall-test-planner project memory.

## Layout
- Static site, no build: `index.html`, `styles.css`, `js/math.js` (plan + read, pure), `js/data.js` (ideas, chips, trial tiles), `js/app.js` (hash router, screens, sliders, sheet/rail, share).
- `assets/character.png` (owner's character, not MIT), `fonts/` (Uncut Sans variable, Geist Mono 400; OFL in `LICENSES/`), `_headers` (CSP etc. for Cloudflare Pages).

## Rules
- One change, every place (owner rule, 2026-10-30): any change the owner asks for is applied in the same pass to the live site, the design canvas (mobile and desktop boards, components) and the project memory. Before saying "done", check all three; never fix only one.
- Design freely, ship on approval (owner rule, 2026-10-31): new things can be drafted on the design canvas without asking, but nothing new goes into the live product until the owner says yes. Fixes he asks for go live as before.
- Nothing typed leaves the browser: no backend, no runtime AI, no third-party requests except Cloudflare Web Analytics (page views only). Last inputs in localStorage (try/catch); share links put inputs after `#`.
- Public sources only; never employer data. Every benchmark keeps its source.
- Mobile-first (390). Desktop (≥1200): the mobile column centred, controls in a 320 rail fixed to the right edge from the top (no “Your test” label on desktop; the mobile peek keeps it, it names the sheet) (top 20, max height = window − 44 px, scrolls inside); “Share plan” (test screen) and “Share result” (decision day) are a fixed button in the bottom-left corner, and idea details float right above it (ideas are reading material); the plan’s Plans row is a tappable row with a chevron that opens the plans editor IN the right column, under the settings (owner, 2026-10-31: all settings live on the right): the column splits into two halves that scroll on their own, the plans half has ✕, closing it gives the settings the whole column back; every rail slider value is a plain number you can click and type into (a fill appears only on hover/while editing), typing updates the answer live (✕ or Esc closes); the top bar holds only the logo; share is a modal. Anything with a scrim (modal, mobile sheet) locks page scroll. Every mobile sheet closes with a swipe down from anywhere in it once it is scrolled to the top (follows the finger; past ¼ of its height or a fast flick it closes, otherwise it springs back; sliders keep their horizontal drag). Mobile: the top bar is sticky and transparent at rest; once the page scrolls (html.scrolled) its background fades in as one long eased gradient (dense behind the logo, then a visible fade ~56 px below the bar, no solid band, no hard edge). No separate shadow under the bar. Desktop: no bar — the logo stays put on the left and the content runs straight to the window edge. Above 1440 the whole page scales (body zoom = width/1440); the page always fills the window and the footer sits at its bottom (#app flex column, footer margin-top: auto; no other spacer on content pages, or the free space splits and notes drift away from their block), the same distance from the edge on every page; every viewport height uses `--vh` (window height ÷ zoom), never raw 100vh, or a blank band appears below the content.
- Motion (transitions.dev tokens), kept to the answer (owner: “too many places”): render() patches the DOM in place within a page (morph). Only elements marked `data-swap` cross-blur (the headline value, week thresholds, decision day), and nothing resizes: the new value takes its place at once and the old one fades out on top of it (`data-swap="center"` for centred text); every other value just changes. Segmented controls in Your test slide one measured pill (tabs sliding; the pill's “placed” flag is a JS property, a data- attribute would be stripped by the morph). Big white choices (weeks, share tones) don't slide: the selected card crossfades (150 ms). Switching Onboarding ↔ Paywall morphs with transitions off and fades the rest in once (only the Testing pill slides). Plan phases, forest plot, verdict range and slider fills glide; sliders don't lag while dragged or typed (UI.instant); a new page rises in; sheet/modal/float animate in and out (closeThen). Everything off under prefers-reduced-motion.
- Start date: edited where it's read — the plan card's “Start …” line is tappable (chevron, hover fill) and opens the native date picker; default = next Monday (whole weeks + a few days to set up); share links carry it as `st`. “Your test” holds only inputs that change the answer, so no date there.
- The character appears only on the start hero; the win verdict is orange, no character (owner, 2026-10-30).
- Mobile verdict: a “Your numbers” row (people per version, chevron) above Share result goes back to the filled results screen to fix a typo (desktop has the numbers in the rail).
- A/B/C reading (owner, 2026-10-30): the results screen starts with a Versions control (A/B · A/B/C, same key as the plan); with three versions each of B and C is read against A with ranges widened for two comparisons (Bonferroni, same split as the plan), the split check is chi-square over three groups, the verdict names the leading version (best clear winner, else best guess), and “Each version against A” shows both on one scale with one no-change line. Links carry `rc`.
- Plans (owner, 2026-10-30): a paywall has 1–4 plans (week, month, year, one-time), each with a typed price, its own free trial (None/3/7/14+, none for one-time) and a share of buyers (0–100% sliders that make room for each other, always adding to 100). Money per view uses the whole mix; the decision waits for the longest trial among plans people buy; the trial question sets every plan's trial; “Your test” shows Free trial only for onboarding. Results ask “Paid · <plan> $<price>” per plan; the source line talks about the priciest plan. Links: `pl=w6.99-50-3_y39.99-50-3`, read numbers in `xa/xb/xc` (people.trials.refunds.paid per plan); old `pw/pa/m` and `ra/rb/rc` links still open.
- Ideas (owner, 2026-10-30: “нужно разнообразие”): a pool of 12 paywall and 14 onboarding ideas, plus 1 and 2 lost ones (only ideas with a published range; no invented numbers) in `data.js`, each with ranges per metric from published tests (Adapty A/B library; onboarding-teardown ranges), never merged, and a `fits()` rule (trial present, annual plan, several plans, one-time plan, onboarding trial). The card shows six that fit the test (“Show all N” reveals the rest in the same order), ranked by the decision metric (money → revenue per user, paid → paid conversion, trials → trial starts); ideas measured on another metric come last with “on <metric>” and are never marked as caught. Goal “not worse”: the card says it is sized to rule out harm, no threshold line.
- Test screen (paywall and onboarding): under the ideas, a “Variant ready? Check it before launch” card links to the variant-check skill in growth-skills (“A and B screens” for a paywall, “A and B flows” for onboarding; owner approved 2026-10-31).
- Onboarding idea ranges follow variant-check `onboarding-mechanics.md`: a “trial conversion (as reported)” figure is never shown as paid conversion. Rebuilt 2026-10-31 after the evidence deep sweep (#1–#167): timeline +13.6–23% trial starts, pre-paywall +60%, sign up later +37%, echo +13% ARPU; “Shorter onboarding” stays lost (cutting steps that ask or set up), its trap names the one test where condensing reading screens won. Results with no control group (before/after, podcast, method not stated) sort below controlled ones on the same metric (owner, 2026-10-31: “опускать ниже”): `weak: { <metric>: true }` on the idea (split and signup trial starts, echo ARPU); the onboarding footnote says “Results with no control group sit below the rest.”
- Lost ideas (owner, 2026-10-31): ideas that lost in published tests (`lost: true` in data.js: onboarding “Shorter onboarding” about −13%, “A loader, then a plan that ignores the answers” about −50%; paywall “The same offer after the main in-app paywall” about −50%) appear only under “Show all”, below the chart in a “Lost in published tests” group, no bar (the axis starts at 0), never ranked or marked as caught; their detail says “Don’t run it hoping for a win”. “Show all N” counts them (onboarding 16, paywall 13). Canvas: VIdeas `lost` prop, board V11IdeasAll.
- Ideas card (owner, 2026-10-31, after two design reviews): a muted line names the metric (“Lift in <metric>, B against A”) above “Your test catches…”; axis ticks read 0, +10%, +20%…; one number = a dot, a range = a rounded bar, with a legend under the chart (“Lowest to highest result” · “One number (one test, or a band given as one figure)”). Rows don’t count tests (owner, 2026-10-31: “не нужно помечать от скольки тестов в графике”); the footnote says where ranges come from, and the idea card lists the tests (`COUNT` in data.js still marks which onboarding metrics come from an Adapty band, for the card’s wording). The idea card lists “Single published tests” (`TESTS` in data.js: app · number, what changed, link; “Several changes at once” / “Offer change” notes), or “No single published test yet.” Only the latest three by publish date are listed (owner, 2026-10-31: “сократи до последних трех”), with a count line under the heading: “Latest 3 of N”, or “N in total” for three or fewer; each `TESTS` entry carries its publish month as a fifth field (undated sorts last). Every test there is a record in growth-skills `evidence/tests.csv`.
- Market splits (owner, 2026-10-31): when one test behind a range reported a different figure by market or platform (`split` on the idea in data.js, from growth-skills evidence `split`), the range keeps the lower figure; the row says it (“iOS only”, “US +27% in one test”) and a hairline to a hollow ring marks the other market; the legend adds “Same test, another market” only when a ring is shown; the onboarding footnote says the chart uses the lower figure and that a single test’s own uncertainty is rarely published.
- Plans editor controls (owner, 2026-10-31): the plan type (Week, Month, Year, One-time) is a dropdown (native select, 44 px, 5% fill, chevron), not a four-way segmented control; removing a plan is a minus button, so it never looks like the panel’s ✕.
- One control size: text fields, sliders and segmented controls are all 44 px tall, radius 10, fill 5% white (owner, 2026-10-30). Every input is at least 16 px text, or iOS zooms in on focus and the page ends up wider than the screen.
- Interface explains itself: no helper notes for obvious controls. Graphics sharp, interface soft. Icons filled.
- Math must match the canvas reference: 50,000 views, 2.75%, 50/50 $6.99/$39.99 → 2/4/6/8 wk = 12.9/9.1/7.5/6.5%; read example A 85,700/1,180/1,177 vs B 85,620/1,050/1,380 → +13% (+5…+21%). Check with a Playwright walk before pushing.
- Agent-readable (owner, 2026-10-31): `index.html` carries a plain-text description and FAQ in `#about` (hidden by CSS, shown in `<noscript>`, removed by app.js on boot) with real planner numbers as examples, a WebApplication JSON-LD, `llms.txt`, `sitemap.xml` and `robots.txt` (Allow + Sitemap; Cloudflare's managed robots.txt is merged in front of it). Keep the FAQ numbers in sync with the math.
